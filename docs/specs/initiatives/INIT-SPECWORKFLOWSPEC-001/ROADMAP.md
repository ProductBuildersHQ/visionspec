## Phase 8 — Follow-ons Surfaced by Phases 5–7 Review

**Theme:** concrete, actionable items the layering, ownership review, and judge calibration surfaced — each scoped from a finding, not speculation

- [x] `RMI-SPECWORKFLOWSPEC-028` Reconcile the two PRD representations before any requirements-family migration (from RMI-025)
  - **Reviewed → decision: they are not two representations of one thing, but three complementary layers over one shared schema; keep them separate.** (1) *PRD as structured data* — prism-roadmap `requirements/prd` (`prd.Document` → generated `schema/prd.schema.json`; section vocabulary in `section.go`; programmatic completeness scoring in `scoring.go`/`completeness.go`; `evaluation_template.go` emits a `rubric.Rubric` **report**, derived from the sections). Consumed only by prism-roadmap's own CLI + schema-gen — not visionspec, not visionstudio. (2) *PRD authoring skeleton* — visionspec workflows' `prd.md` (blank template). (3) *PRD LLM-judging rubric* — visionspec's `prd.rubric.yaml` (a `RubricSet` **definition**, hardened + layered). The shared substrate is **structured-evaluation** (prism-roadmap emits its `Rubric` report; visionspec consumes its `RubricSet` definition) — same schema package, different roles, no collision.
  - **Vocabulary homes (the crux):** prism-roadmap has **one** canonical, section-schema-derived evaluation vocabulary (single source); visionspec has **15** per-workflow `prd.rubric.yaml` files with intentionally methodology-specific categories (google's peer-review, stripe's SDK/API, AWS's Leadership Principles — per RMI-024). prism-roadmap's `section.go`/`prd.schema.json` is therefore the natural canonical anchor for PRD *structure*, while the per-methodology *judging* vocabularies should stay distinct.
  - **Consequence:** RMI-025's "move templates to prism-roadmap" is retired as mis-scoped — the template is the *authoring* layer (belongs with the workflows), prism-roadmap owns the *data-model* layer; they are different concerns, not a duplication to consolidate. No code change.
  - **Optional backlog (not required):** if a hybrid programmatic-plus-LLM PRD score is ever wanted, align prism-roadmap's `evaluation_template.go` category vocabulary with visionspec's hardened rubric and add the v0.14.0 layered metadata (`class`/`blocking`/`evaluation`) to it, so the two scores compose. Deferred; not part of this initiative.
- [x] `RMI-SPECWORKFLOWSPEC-029` Backport N/A-with-rationale applicability to the lighter family rubrics' blocking categories (from RMI-026)

Added `not_applicable` (N/A-with-rationale, matching the hardened enterprise/aws pattern) to the 6 conditional blocking categories that assume a service/feature: trd's `api_design`, `data_models`, `security_considerations`, `dependencies` and prd's `user_stories`, `success_metrics`. Universally-applicable gates (goals, requirements, problem, plan/roadmap execution) intentionally keep no escape hatch. This closes the RMI-026 finding — the initiative's own library TRD would now score `security_considerations` as not_applicable-with-rationale (pass) instead of a false-negative block. Guarded by `TestConditionalBlockingCategoriesAllowNA`; full suite + vet + gofmt + golangci-lint + `prism-sync -check` clean. The methodology-specific family rubrics (startup, google, stripe, etc.) are lower-risk — applied within their own domain where categories are more likely to apply — and left as an optional extension.
